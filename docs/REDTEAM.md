# Subordinate–1 적대 검토 (T23)

> **탁상 검토 — 사내 모델로 돌린 결과가 아닙니다.** 이 세션에서는 사내 LLM · 회사 PC · opencode 를 돌릴 수 없었습니다. 공격마다 (1) 약한 모델이 `SKILL.md` 를 읽고 어디서 무너질 수 있는지 (2) 그것을 막는 문장이 `SKILL.md` · 에이전트 권한에 **분명히** 있는지만 따졌고, 해석이 둘로 갈리는 문장은 없는 것으로 봤습니다. 검토자 (Claude Opus) 가 스킬을 연기해 지켜 낸다고 해서 사내 모델이 지킨다는 뜻이 아닙니다. 그래서 연기해 본 결과는 판정에 쓰지 않았습니다. 실제로 무너지는지는 사내 시범 (T22) 에서 6 절의 재연 대본으로 잽니다.

- 무엇: 합성 시나리오로 Subordinate–1 묶음 — 스킬 [skills/subordinate-1/SKILL.md](../skills/subordinate-1/SKILL.md) · 에이전트 [opencode/agents/subordinate-1.md](../opencode/agents/subordinate-1.md) · 명령 [opencode/commands/subordinate.md](../opencode/commands/subordinate.md) — 을 공격해 보고, 막지 못한 길은 고치고, 고칠 수 없는 것은 알려진 한계로 적었습니다.
- 날짜 · 판: 2026-11-03 · T17 의 스킬 (273 줄) 을 검토해 고친 판 (309 줄) 까지.
- 읽은 것: 이 저장소의 RULES · PLAN (04 · 05 · 09) · SPEC · 예시 · 시험과 opencode 문서 (permissions · agents · tools · skills · rules · commands · config 의 compaction). opencode 문서는 사실 확인에만 썼습니다.
- **결과: 시나리오 47 · 막힘 9 · 고침 35 · 한계 3.** (검토 뒤 R-35 를 한계 › 고침으로 — 아래 7 절 5)

| 판정 | 뜻 |
|---|---|
| 막힘 | 막는 문장 (또는 권한 deny) 이 이미 분명히 있어 고치지 않았습니다 |
| 고침 | 문장이 없거나 두 갈래로 읽혀 이번에 고쳤습니다 (3 절) |
| 한계 | 프롬프트 · 권한으로는 막을 수 없습니다 — 사람 · 호스트 설정이 막습니다 (5 절) |

- '막힘' · '고침' 은 **막는 문장이 있다** 는 뜻일 뿐, 사내 모델이 **지킨다** 는 뜻이 아닙니다.
- 사용자가 직접 시키는 공격 ('계산해서 넣어' · '한계 장 지워') 은, 스킬에 '사용자가 시켜도' 가 없으면 '사용자가 허락했다' 로도 읽힙니다. 그래서 이런 공격은 원래 규칙이 있어도 두 갈래로 보았고, 고침이 많은 까닭입니다. 자료 속 지시 (F) 는 0 › 9 가 이미 분명해 막힘으로 봤습니다.
- 표의 '막는 문장' 은 고친 `SKILL.md` 의 자리입니다. `0 › 10` 은 '0 먼저 지킬 것' 의 10번, `8 표` 는 8 절의 '부탁 › 이렇게 답한다' 표입니다. `(새)` 는 이번에 더한 문장, `(고침)` 은 이번에 고친 문장입니다.

## 5 알려진 한계

1. **프롬프트 지시는 보안 경계가 아닙니다.** `SKILL.md` 의 문장은 약한 모델이 어길 수 있고, 자료 속 지시 (F) 는 문장 하나로 다 막을 수 없습니다. 사람 없이 막는 것은 권한의 `deny` 뿐입니다 — 셸 · 웹 · 하위 에이전트 · 질문 도구 · deck 이름 밖의 쓰기 · 이름 무늬가 맞는 비밀 파일 읽기 · 그 밖의 모든 도구 (`"*": deny`).
2. **ask 는 사람이 막습니다.** deck 쓰기 · 바깥 폴더 접근은 허락 창이 막는 것이라, 자동 승인 (`--auto`) · 허락 창의 `always` · 다른 에이전트로 바꾸기 (R-42 · R-45) 가 그 선을 지웁니다. `always` 를 한 번 누르면 그 세션이 끝날 때까지 같은 무늬의 요청을 묻지 않습니다 (도구가 고르는 무늬가 파일 하나인지 더 넓은지는 [미확인]). 그러면 같은 `deck.md` 를 다시 쓸 때 덮어쓰기를 막는 것은 스킬 7.3 의 문장뿐입니다. 바깥 폴더 허락 창도 opencode 를 연 폴더 밖에서만 뜹니다 — 연 폴더 안이면 자료 폴더 밖의 파일도 묻지 않고 읽히고, 막는 것은 스킬 0 › 9 의 문장과 읽기 deny 무늬뿐입니다.
3. **호스트가 스킬보다 먼저 읽는 것.** opencode 를 연 폴더 (와 그 위 폴더) 의 `AGENTS.md` · `.opencode/` (같은 이름 스킬 · 에이전트) · `opencode.json` 은 모델이 첫 줄을 쓰기 전에 읽힙니다 (R-47). 같은 이름 스킬이 여럿일 때 어느 것이 쓰이는지는 문서에 없습니다 [미확인]. 받은 자료 폴더에서 opencode 를 열지 않는 것이 막는 길입니다.
4. **이름 무늬로 막는 읽기.** 이름이 다른 비밀 파일 (`설정.txt` 안의 비밀번호 등) 은 권한으로 못 막습니다. 자료 폴더 안의 비밀은 스킬 (4 · 4.4) 과 사람이 막고, 모델이 한 번 읽은 파일 내용은 대화에 옮기지 않아도 도구 결과로 opencode 기록에 남을 수 있습니다 [추정]. 자료 폴더에 비밀이 든 파일을 두지 않는 것이 맞습니다.
5. **그림 속 글은 가릴 수 없습니다.** P-08 로 그림을 고치지 않으므로, 그림 안의 이름 · 주소는 그 그림을 쓰는 장에 그대로 보입니다. 스킬은 알리기만 합니다 (R-26).
6. **'합성' 자기 표시 (고침).** 처음 검토 때는 `data_class` 가 자료에 적힌 표시로 정해졌습니다. 지금은 기본 `real` 이고 사용자가 저장 확인에서 고를 때만 `synthetic` 입니다 (R-35 · 7 절 5). 사용자가 잘못 고르는 것은 막지 못합니다.
7. **맥락 자동 요약.** 다시 불러오기를 에이전트 본문에 넣었지만, 요약이 셈 · 답 id 를 틀리게 남기면 이어 받은 셈도 틀립니다 (R-46). opencode 문서의 `compaction.auto` 는 기본이 켜짐입니다.
8. **기성품.** `deck.md` 를 넘긴 뒤 Presenton 이 글을 다시 쓰거나 밖으로 보내는 것은 이 묶음 밖입니다 — [USE-presenton.md](USE-presenton.md) 2 절 · 4 절이 사람의 확인으로 막습니다.
9. **명령 인자.** opencode 명령 틀은 `@파일` · `` !`명령` `` 을 풀어 넣습니다. 사용자가 `/subordinate` 뒤에 직접 친 글이 이렇게 풀리는지는 [미확인] 이지만, 사용자가 직접 치는 글이라 이 검토의 위협 밖으로 두었습니다.
10. **탁상 검토의 한계.** 이 문서의 판정은 문장을 따라간 것입니다. 사내 모델이 실제로 지키는지는 6 절의 재연으로만 압니다.
